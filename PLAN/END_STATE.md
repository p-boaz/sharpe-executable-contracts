# Canonical End State

This document defines the intended end state for this repository.

It is based explicitly on the Sharpe hackathon executable-contracts brief:

- https://github.com/hdubugras/sharpe-hackathon?tab=readme-ov-file

## The One-Sentence Goal

Given contract Markdown, this repo should produce an executable contract representation, generate concrete scenario data with an LLM, run the contract against that data to compute outcomes, and deterministically compile the executable representation back into readable English without using an LLM.

## What "Done" Means

We are done when a judge can take a Markdown contract, run fewer than 10 documented steps, and inspect:

- the contract input
- the executable representation
- the scenario/fact data used for execution
- the computed execution result
- the deterministic English regenerated from the executable representation

The output must show real computation, not just structure.

## Required Capabilities

### 1. Contract Markdown -> executable form

The system must ingest `.md` contract text and produce a structured executable representation.

That representation must encode, at minimum where supported by the contract:

- obligations
- conditions
- deadlines / timing rules
- formulas or money calculations
- penalties / fee triggers

Partial coverage is acceptable, but it must be explicit and honest.
Unmodeled clauses should be marked as such, not silently dropped or pretended to be executable.

### 2. LLM-generated scenario data for arbitrary contracts

The pipeline must include an LLM step that proposes or fills in structured scenario data so execution can run on unseen Markdown contracts.

That scenario data should be inspectable and stored as an explicit artifact.
Judges must be able to see what facts were fed into the executor.

Hand-authored fixtures are acceptable for local testing, but they are not the end state.

### 3. Real execution

The system must run the executable representation against concrete scenario data and compute outcomes.

A successful run should visibly evaluate things like:

- whether obligations were met or breached
- whether conditions triggered
- monetary amounts due
- fees, interest, or penalties
- state transitions over time

If the executor does not perform real evaluation, we are not done.

### 4. Deterministic executable -> English

The executable representation must compile back to readable English through normal program logic only.

Rules:

- no LLMs in this step
- same executable input -> same English output every time
- regenerated English should preserve the meaning of what the executable actually encodes

This path should be easy to inspect and easy to prove deterministic.

### 5. End-to-end demoability

The repo must provide a base demo in fewer than 10 numbered steps.

That demo must show:

- exact input contract
- exact command(s) to run
- where outputs appear
- how to inspect the scenario input
- how to inspect execution output
- how to verify deterministic English

## Quality Bar

The target is a compact, credible MVP for the hackathon, not a full legal reasoning platform.

That means:

- optimize for a working end-to-end pipeline
- prefer explicit, inspectable artifacts over hidden behavior
- favor honest limits over fake completeness
- keep code and IR simple enough to debug quickly
- generalize beyond one hardcoded contract shape

## Non-Goals

These are not required for the repo to be considered done:

- full legal correctness
- full contract coverage
- court-ready drafting quality
- support for every contract family
- sophisticated legal ontology or heavy abstraction layers

## Repo-Level Acceptance Criteria

At the end of the project, this repo should satisfy all of the following:

1. `run` accepts a Markdown contract and writes `ir.json`, `scenario.json`, `execution.json`, and `english.txt`.
2. `scenario.json` is generated by a pipeline that includes an LLM-based scenario step for unseen contracts.
3. `execution.json` shows real computed outcomes from explicit scenario inputs.
4. `english.txt` is generated deterministically from the executable representation and does not use an LLM.
5. `determinism` proves the executable-to-English path is stable across repeated runs.
6. The system works on at least one sample contract cleanly and is built to degrade honestly on held-out contracts.
7. The README documents a judge-usable base demo in fewer than 10 steps.

## Simple Decision Rule For Future TODOs

We should prioritize work that most improves one of these:

- executability
- deterministic English regeneration
- scenario generation for unseen contracts
- honest partial coverage
- judge clarity and inspectability

If a task does not move one of those directly, it is secondary.
